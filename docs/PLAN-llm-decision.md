# LLM 与 Decision 接入实施计划

日期：2026-11-17。状态：待实施。本文定义开发范围、执行顺序和验收标准，不表示相关功能已经完成。

## 1. 交付目标

让用户通过本地命令输入自然语言目标，LLM 将其转换为结构化目标和任务图，Decision 驱动已注册技能执行，并以实际观测确认结果。运行中可以停止、修改目标；失败时有限恢复并报告原因。

首批技能为 `navigate` 和 `openContainer`。第一阶段导航限定为已加载、已知、同维度的平坦地形；支持平地绕障，不承诺高差、跑酷或复杂碰撞地形。完整物理校准、连续跳跃、挖掘、放置、合成和通用背包操作另列后续工作。

完成示例：

- “走到 4 1 0”：接受目标、规划路径、执行、观测确认到达、返回结果。
- “走到 4 1 0 的箱子旁并打开”：规划至可交互邻接位置，确认距离与视线，打开容器并以窗口反馈确认。
- “停下”：本地直接取消，无须等待 LLM。
- 执行中“改去 2 1 5”：撤销旧版本任务与请求，接受新目标，迟到结果不能恢复旧动作。
- “打开那个箱子”：没有唯一可定位目标时请求澄清，不猜测坐标。

目标按可验证的用户意图建模，例如 `navigateToPosition`（目标坐标与维度）和 `openContainerAt`（容器定位信息及交互要求）。目标完成条件由运行时根据目标类型和已注册技能生成并验证；任务图全部成功只是必要证据之一，不能单独代表目标完成。比如只到达箱子旁、遗漏开箱步骤，或到达与请求坐标不符的位置，都不能报告目标成功。

## 3. 架构与责任边界

```text
本地命令 → 指令路由 → 意图/澄清 → GoalStore
                                 ↓
技能目录 + 当前观测 → LLM 计划 → 计划校验与版本检查
                                 ↓
                       Decision 持续调度
                                 ↓
                      技能 → Planner/Controller
                                 ↓
                        实际观测 → 结果验证
                                 ↓
                   继续执行 / 局部恢复 / 有限重规划
```

- LLM 只生成意图、任务建议和用户回复，不直接调用驱动或写按键。
- Decision 管理目标、选择任务和恢复策略；不进入每个物理 tick 的控制计算。
- 目标类型、目标定位信息和用户约束形成结构化契约；运行时为每种目标类型定义完成谓词，并结合实际观测验证。模型可提出目标及任务建议，但不能定义或放宽完成谓词、把任务全部成功直接声明为目标完成，也不能任意定义资源权限或抢占权限。
- 技能拥有参数 schema、资源声明、超时边界和结果验证器。目标成功必须同时满足运行时目标谓词及其要求的技能结果证据。
- Controller 是唯一动作写入者，保留现有租约身份、generation、原子交接和迟到写入拒绝保护。
- 服务端验收采样不进入在线模型上下文或 Decision 观测。
- 沿用各包 `src/index.ts` 公共入口；`main.ts` 只负责装配，将运行循环放入职责文件。

## 4. 分阶段工作包

### A. 契约、配置和技能目录

建议涉及：`packages/contracts/src/{schemas,types}.ts`、`packages/decision/src/skill-registry.ts`、`packages/llm/src/schemas.ts`、`apps/bot/src/config.ts`。

1. 区分模型建议与运行时对象：模型提供目标文本、坐标和约束；运行时生成 sessionId、goalId、revision、任务 ID 和请求 ID。模型不能提升运行时优先级。
2. 增加澄清响应、目标状态和结构化失败原因。目标状态至少包括 planning、running、awaitingClarification、succeeded、failed、cancelled；运行时维护结构化目标类型、经确认的定位信息与约束，并派生不可由模型覆盖的完成谓词。
3. 注册技能定义：ID、说明、参数 schema、资源、允许的超时范围、抢占策略、执行器和验证器。
4. 计划接纳采用整批原子校验：技能、参数、依赖、环、任务数量、目标关联、有效期和资源策略全部通过后才入库。资源与验证规则由技能定义派生。
5. 首版环境配置：`LLM_PROVIDER=offline|openai-compatible`、`LLM_BASE_URL`、`LLM_API_KEY`、`LLM_MODEL`；运行预算通过有默认值的配置项管理。
6. 使用 Node 24 的显式 env-file 启动方式读取根目录 `.env`，不隐式扫描任意目录。新增 `.env.example` 并忽略 `.env`、`.env.*`，保留示例文件。
7. 未配置真实模型时使用 offline；显式选择真实 Provider 却缺少必填配置时启动失败并给出明确提示，不静默回退。

验收：未知技能、非法参数、循环依赖或超出权限的计划不会留下部分任务；日志与示例不含 API Key。

目标验收另须证明：目标谓词所需步骤缺失时整批计划拒绝或目标保持未完成；`openContainerAt` 仅导航到箱子旁不能成功；导航目标坐标/维度不匹配时，即使任务报告成功也不能把目标标为 succeeded。

### B. Decision 持续调度与取消

建议涉及：`goal-store.ts`、`utility-selector.ts`、`task-graph-executor.ts` 和新增 `runtime.ts`。

1. 首版仅运行一个前台动作任务；允许维护多个待执行目标，暂不实现无冲突任务并行执行。
2. 由目标、任务结果、观测失效等事件唤醒调度，防止重复运行和空转。依赖完成后继续下一层任务；任务图全部成功后仍须单独评估运行时目标完成谓词，不满足时进入恢复或失败，不能标记目标 succeeded。
3. 候选必须满足能力、前置条件、计划时效和资源条件。先比较运行时目标/任务优先级，再比较现有 utility 分数，同分使用稳定 ID 排序。
4. 高优先级任务可触发可抢占任务交接；同优先级沿用 holdMs 和 hysteresis。不可抢占任务不被普通切换打断。资源取得仍以 LeaseArbiter 原子申请结果为准。
5. 修正滞回比较使用旧分数的问题，比较当前仍有效候选的最新分数。
6. 停止、目标修改、目标截止时间、断线和维度切换沿同一取消链传播至模型、规划器、技能与输入控制。
7. 异步结果绑定 sessionEpoch、goalId、revision 和计划代次；同一目标版本的再次规划也必须隔离旧任务。取消后的迟到成功不能覆盖终态。
8. 任务超时标记为超时失败，与用户取消分开；失败依赖不再执行，下游目标进入恢复或失败状态。

验收：多层 DAG 自动完成；普通高优先级抢占有效；遗漏必要技能、错误目标位置或目标谓词缺少观测证据时目标不成功；本地停止在下一次调度释放持续输入；旧请求、旧任务和旧租约都不能继续写入。

### C. 真实 LLM 与请求协调

建议涉及：`provider.ts`、`request-coordinator.ts`、`context.ts` 和新增 `openai-compatible-provider.ts`。实际实现前核对所选服务的官方接口文档，首版固定一种经过验证的请求/响应协议，不假定所有兼容端点行为相同。

1. 提供意图、规划、回复三类调用；结构化输出由 Zod 最终校验。普通聊天回复不能进入计划执行通道。
2. 输入包含用户目标、可定位观测、技能目录、当前任务和最近失败证据；保留 UTF-8 上下文预算，超预算返回明确错误。
3. 补充最小约束表达，例如禁止破坏方块、限定维度、指定目标和截止时间；计划不得丢失已确认约束。无法表达或执行时澄清或拒绝。
4. 请求协调按会话/目标隔离，避免一个目标的请求错误取消另一个；停止指令优先于所有模型调用。
5. 初始默认：单次请求超时 10 秒；每目标最多 8 次实际 API 尝试，包含意图、规划、回复、重试和修复；并发请求上限 1。
6. 仅对暂时网络错误、429 和可恢复 5xx 最多重试 1 次，遵守总截止时间与可用的 Retry-After；认证错误和其他确定性参数错误不重试。
7. 不合法结构化输出最多修复 1 次，同样计入调用预算；耗尽预算返回结构化失败，保留本地停止和状态查询。
8. 记录请求类型、耗时、状态、模型、服务端返回的 token 用量；未知用量和费用明确标记不可得，不能将其视为零。配置价格后才计算费用。
9. 远端未配置、401、429、格式不合法、超时和取消分别给出稳定错误码；异常和日志需移除密钥及认证头。

验收：模拟 HTTP 服务覆盖成功、认证失败、429、超时、取消、格式修复、调用预算和迟到响应。真实接口验证单独记录使用的服务与模型，不把模拟服务结果表述为真实 API 已通过。

### D. 在线观测和首批技能

建议涉及：`packages/world`、`packages/controller`、`packages/planner` 和 `apps/bot/src/skills/`。

1. 为在线导航导入附近已加载区块中的实际方块，处理加载、卸载、方块更新和维度重置；不扫描无限世界，不把未知格视为空气。
2. 初始导入与后续更新纳入可排序的观测流程，记录来源和版本；补齐所需实体与背包事件，避免世界快照仅有 revision 没有技能所需证据。
3. `navigate` 使用现有平地 A\* 和受租约控制的物理 tick 输入，校验路线依赖；实现到达容差、实际制动、无进展检测、路径失效和有限局部重规划。
4. 支持的平地障碍可绕行；半砖、楼梯、水和高差等未支持地形应明确拒绝，不能以 solid/empty 简化结果宣称完整碰撞支持。
5. `openContainer` 以指定方块为交互目标，导航至有支撑、可站立、满足距离和视线的邻接位置，不能把箱子实体格作为导航终点。
6. 开箱状态转换分别定义为：提交后等待对应 requestId 的窗口打开证据（`submitted → observedOpen`），驱动明确拒绝则 `submitted → rejected`；超时或连接状态变化但结果不明则 `submitted → uncertain`。`uncertain` 后最多等待 5 秒对账，只接受同一目标方块、requestId 和会话 epoch 的证据。窗口打开可确认副作用已发生；窗口关闭本身不能证明旧请求以后不会打开。任何迟到窗口事件都记到原 requestId，不能恢复旧目标或作为新目标的成功证据；旧回调不得关闭或修改新请求打开的窗口，窗口清理由 Controller 按当前租约和窗口所有权处理。
7. 对账超时仍无确定结果时，将对应目标置为 `failed(reason=interaction_outcome_unknown)`，交互屏障独立保留，避免目标终态被误认为底层请求已结束。屏障只在原请求确认 settled 且完成可信窗口同步后，或连接 epoch 重置并重新观察窗口状态后解除；收到窗口关闭事件但原请求仍 pending 时不得解除。停止或替换会立即撤销旧目标的移动/规划和模型请求，但不能撤销已发送的开箱副作用；新目标可继续执行不依赖交互的技能，所有开箱请求在屏障解除前均被拒绝。重连也不得自动重放未完成开箱。
8. 断线后立即清理动作和请求。首版不自动恢复未完成任务，重新连接后需重新提交；持久化事件用于追踪，不宣称已有任务断点续跑。

验收：平地到达、绕障、运行中阻挡、未知区块、开箱、交互距离/视线拒绝、停止和断线均有确定结果。模拟开箱永不返回时，有限对账后目标以 `interaction_outcome_unknown` 失败且交互屏障保留；窗口关闭不能单独解除仍 pending 的请求屏障；原请求 settled 并完成同步或重连重新观察后才可解除；停止/替换后的迟到窗口事件不会复活旧目标或成为新目标成功证据，旧回调不会关闭新窗口，也不自动重放旧副作用。实服验收使用本地受控夹具，并保留输入与观测日志。

### E. 反馈、恢复、指令入口与记录

建议涉及：`apps/bot/src/{runtime,commands,main}.ts`、`packages/decision`、`packages/memory`、`packages/replay`。

1. 本地终端提供 `/goal <自然语言>`、`/status`、`/stop`、`/replace [--goal <goalId>] <自然语言>` 和 `/clarify <goalId> <revision> <回复>`；`/status` 展示每个目标的 ID、revision 和状态。每次进入新一轮澄清都递增 revision，避免旧回复与新问题同版本；回复必须携带待澄清目标当前显示的 ID 和 revision，已取消、已替换或版本不匹配时拒绝。允许多个待执行目标，但同一时刻仅一个前台动作目标。`/stop` 本地取消当前活动目标，并取消所有排队及等待澄清的目标，清空其自动续跑资格；停止后不会因队列中尚有目标而自动继续，用户须显式再次提交目标。`/replace --goal <goalId>` 替换指定目标；省略参数时仅当恰有一个非终态目标时接受，否则本地列出候选 ID 并要求重新指定，不调用模型猜测。使用显式 `--goal` 标记，避免自然语言首个 token 与目标 ID 混淆。无需先接游戏聊天或增加 Web UI。
2. 明确区分 accepted、awaitingClarification、running、completed、failed、cancelled；完成结论由运行时目标谓词和实际观测产生，任务图完成本身不足以结束目标，模型只可润色已验证事实。
3. 路线变化优先本地重规划：每任务最多 2 次；无法局部恢复时每目标最多 2 次 LLM 重规划，仍受总 API 预算约束。
4. 只对相关观测变化触发恢复，合并重复通知，避免每个 tick 都请求模型。不可达、缺能力和未完成副作用使用各自策略，不能统一无限重试。
5. SQLite 与 NDJSON 记录目标版本、计划代次、请求状态、接纳/拒绝理由、选择与抢占、技能结果和重规划原因。保存可重放的已校验响应，默认不保存认证信息和完整原始请求。
6. 统一事件序号与单调时间，记录异步完成和接纳顺序。Decision 回放使用已记录模型与规划结果，不再次调用真实 API；确定性算法重算仍独立验证。
7. 退出时撤销任务、释放按键、取消请求、关闭连接并刷新存储；重复关闭保持幂等。
8. 更新 README、维护指南和 IMPLEMENTATION，区分实现完成、离线验证、真实 API 验证及在线动作验证。

验收：两个首批示例均走通；改口和停止不依赖模型响应；失败分类可查询；日志可重放调度过程，且不重复产生在线动作。多目标测试覆盖 `/stop` 后队列不自动启动、带 ID 替换指定目标、多个候选时省略 ID 被拒绝、澄清绑定 revision 以及过期澄清被拒绝；`/status` 能区分目标版本与状态。

## 5. 依赖顺序与委派

顺序为 A → B → C → D → E。A 完成后可分别推进 Provider 与在线技能，但必须在集成前固定公共契约。

按 AGENTS.md，开始实现后将实现与相关测试委派给 `development_assistant`。每个工作包明确文件所有权，告知执行者共享工作区且不得回退其他修改。主代理负责契约审查、依赖协调、集成验证和交付汇总。

建议分批交付：

1. **Decision 可用**：A + B，使用固定 Provider 和记录驱动验收调度、抢占与取消。
2. **模型接入可用**：C，真实 Provider 可配置，模拟 API 契约与异常测试通过。
3. **在线最小闭环**：D + E，实际完成导航和开箱，并完成有限恢复与结果报告。

## 6. 测试与最终验收

| 层级       | 必须覆盖                                                               | 通过意味着什么           |
| ---------- | ---------------------------------------------------------------------- | ------------------------ |
| 单元与契约 | 参数/DAG 校验、目标完成谓词、预算、优先级、抢占、超时、取消和迟到结果  | 模块规则成立             |
| 模拟集成   | 固定/模拟 Provider → 多层任务图 → 记录驱动 → 观测结果                  | 软件闭环成立             |
| API 集成   | 指定真实模型的结构化输出、错误提示、取消和使用量                       | 该模型接口可用           |
| 本地 Paper | 导航、绕障、开箱对账、交互隔离、阻挡恢复、多目标命令、改口、停止和断线 | 首批在线技能可用         |
